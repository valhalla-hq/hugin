# Screenshot clipboard preservation

## Evidence and cause

The manual Codex attempt at 09:17:25 MESZ captured the native target and field,
then rejected delivery as `format_unsupported` / `clipboard_failed`. This is a
different path from the earlier `target_changed` field-focus rejection.

A fresh user-provided screenshot copy was inspected without reading image
contents. Native formats: DataObject, CF_BITMAP, PNG,
CanUploadToCloudClipboard, CanIncludeInClipboardHistory, Ole Private Data,
CF_DIB and CF_DIBV5. A separate bounded read-only OLE enumeration reports
bitmap/GDI, PNG/IStream and the two policy DWORDs/HGLOBAL, with content aspect,
index -1 and no target device. The existing whitelist rejects the registered
PNG/policy formats and OLE bookkeeping before clipboard mutation.

## Change

The native producer owns format enumeration and the closed raster policy.
PNG and history/cloud policy bytes are retained alongside DIB/DIBV5. Bitmap is
regenerated by Windows from DIB. The two OLE bookkeeping formats are omitted
only after complete public OLE metadata proves this closed raster bundle.
Hidden/unknown formats, storage/file media, indexed content, target devices,
incomplete enumeration and unrelated OLE text bundles remain unsupported.

The metadata helper releases the clipboard before OLE calls, has a 2-second
deadline and 256-MiB process-family memory cap, emits at most 2048 bytes, and
retains ownership on failed cleanup. No image bytes or COM pointers cross its
protocol. Its proof is bound to the exact sequence and native format order;
the caller rechecks both under the clipboard lock before materializing bytes.
The existing 32-MiB snapshot limit, transaction ownership, target checks and
restoration rules remain in force. Ordinary non-OLE cases avoid the helper.

Temporary dictation text is explicitly excluded from clipboard history/cloud
processing. Original screenshot policy bytes are restored unchanged. No Windows
settings are changed. The approved UI, animation, original sounds, voices and
worker dependencies are unchanged.

## Verification

- 462 contract/integration tests with Python 3.12.10 and `-S`: pass, 20.769 s.
- 60 focused policy, ABI and clipboard checks: pass, 0.009 s.
- Separate specification/standards reviews found no product-path issue.
- Native synthetic OLE bitmap/PNG-stream/policy roundtrip: pending final run.
  The fixture publishes only after a final expected-sequence check and never
  adopts a later snapshot sequence as restoration authority. Its opt-in setup
  requires a disposable text clipboard and no concurrent copying: OLE publication
  has no atomic compare-and-replace API. The fixture uses its own message-only
  Edit for WM_PASTE, never Codex input or foreground manipulation.
- The first native fixture exposed a fixture error: its IStream exit position
  was zero, which denotes empty transferred data. The producer now leaves the
  stream at its data end; the independent stream reader seeks to zero. Production
  snapshot guards were not loosened in response.
- One pre-existing ABI expectation was stale on untouched base c378743: the
  second sequence check follows native-target validation. The expected order
  now matches that existing production behavior; commit_paste is unchanged.

The helper's runtime/memory limits are enforced bounds, not measured usage.
No token, CPU or peak-family-memory performance claim is made. The final native
probe and human Codex screenshot/dictation acceptance remain required.
